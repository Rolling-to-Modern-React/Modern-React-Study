## 2.5.2 주장 2: 렌더링 과정은 비용이 비싸다. 모조리 메모이제이션해 버리자

### 핵심 개념 요약

요약 : React 최적화는 확신이 없을 때, 가능한 모든 곳에 메모이제이션(`memo`, `useMemo`, `useCallback`)을 적용하는 것이 잠재적인 위험 비용을 줄이는 더 나은 전략이다.

**메모이제이션 적용의 딜레마**

모든 개발자는 "성능이 중요한 컴포넌트(자주 렌더링되거나, 연산이 비싸거나, 자식이 많은 경우)에 메모이제이션을 적용하면 성능에 도움이 된다"는 사실에 동의한다.

*두 가지 선택권*

1. **이상적인 방법:** 컴포넌트를 분석해 **필요한 곳에만 선별적으로** `memo`를 적용한다.
2. **현실적인 방법:** **일단 모든 곳에** `memo`를 적용한다.

현실적으로 1번(선별 적용)은 프로젝트 규모가 커지고 복잡해지면 지키기 어려우며, 2번(전부 적용)이 났다고 함

**`memo` 적용 vs 미적용 (비용 분석)**

2번 주장을 뒷받침하기 위해, `memo`를 잘못 사용했을 때의 비용과 사용하지 않았을 때의 잠재적 위험 비용을 비교

- 불필요한 곳에 `memo`를 적용한 비용
    - `memo`를 적용하면 발생하는 유일한 비용은 **`props`에 대한 얕은 비교(shallow comparison) 비용**뿐
    - "이전 렌더링 결과를 저장하는 메모리"는 비용으로 보지 않습니다. 어차피 React는 재조정(diffing)을 위해 가상 DOM의 이전 결과물을 항상 저장하고 있기 때문
    - 물론 `props`가 매우 복잡하면 이 비교 비용도 커질 수 있지만, 상대적으로 적은 비용으로 간주
- 필요한 곳에 `memo`를 적용하지 않은 비용 (잠재적 위험)
    - 불필요한 **컴포넌트 렌더링** 발생
    - 컴포넌트 내부의 **복잡한 로직 재실행**
    - 위 두 가지 문제가 **모든 자식 컴포넌트에서 반복적**으로 발생 (연쇄 작용)
    - React가 이전/이후 트리를 비교하는 **재조정(Diffing) 비용** 발생

⇒ 얼핏 봐도 `memo`를 적용하지 않았을 때 발생할 수 있는 **잠재적 위험 비용이 훨씬 더 큽니다.**

**`useMemo`와 `useCallback`: 참조 투명성**

이러한 논리는 `useMemo`와 `useCallback`에도 동일하게 적용

```tsx
function useMath(number: number) {
	const [double, setDouble] = useState(0)
	const [triple, setTriple] = useState(0)
	
	useEffect(() => {
		setDouble(number * 2)
		setTriple(number * 3)
	}, [number])
	
		return { double, triple }
	}
	
export default function App() {
	const [counter, setCounter] = useState(0)
	const value = useMath(10)
	
	useEffect(() => {
		console.log(value.double, value.triple)
	}, [value]) // 값이 실제로 변한 건 없는데 계속해서 console.log가 출력된다.

	function handleClick) {
		setCounter((prev) = prev + 1)
	}
	
	return (
		<>
			<h1>{counter}</h1>
			<button onClick={handleClick}>+</button>
		</>
	)
}
```

- 문제상황
    - `useMath` 훅은 내부 값(`double`, `triple`)이 같더라도 **매번 새로운 `{ double, triple }` 객체를 생성**해서 반환
    - 이 훅을 사용하는 `App` 컴포넌트가 (상관없는 `counter` 상태 변경으로) 리렌더링되면, `useMath`가 다시 호출
    - `value`는 **참조가 다른 새 객체**가 됨
    - `useEffect`는 `[value]` 의존성을 가지므로, 참조가 달라졌다고 판단하여 **실제 값이 변하지 않았음에도 매번 다시 실행**

```tsx
return useMemo(( => (f double, triple }), [double, triple])
```

- 해결 책
    - `useMath`의 반환 값을 `useMemo`로 감싸, 내부 값(`double`, `triple`)이 변경될 때만 새로운 객체를 생성
- **참조의 투명성**
    - 메모이제이션은 단순히 현재 컴포넌트의 리렌더링을 막는 것뿐만 아니라, 이 컴포넌트(혹은 훅)가 반환하는 값의 참조를 고정(유지) 시켜 줌
    - 이 값을 사용하는 다른 컴포넌트나 `useEffect` 등이 값이 실제로 변하지 않는 한, 참조도 변하지 않을 것이라는 참조 투명성을 가지고 동작할 수 있게 함

**결론**

- `memo`, `useMemo`, `useCallback`과 같은 메모이제이션은 ‘잘못 사용했을 때의 비용’보다 ‘실수로 빠뜨렸을 때 치러야 할 위험 비용’이 훨씬 큼
- 섣부른 최적화라 할지라도, **최적화에 대한 확신이 없다면 가능한 한 모든 곳에 메모이제이션을 활용하는 것이 더 많은 이점을 누릴 수 있는 전략이다.**
