## 2.4.2 리액트의 렌더링이 일어나는 이유

### 핵심 개념 요약

#### 렌더링(Rendering)의 발생 시점
리액트에서 렌더링은 “UI를 새로 계산해야 하는 상황”에서 발생한다.  
렌더링이 일어나는 대표적인 시나리오는 다음과 같다.

---

### 최초 렌더링
- 사용자가 애플리케이션에 **처음 진입했을 때** 발생한다.  
- 브라우저에 보여줄 **초기 UI 트리**를 구성하기 위해 수행된다.  
- 앱의 루트(`ReactDOM.createRoot`)에서 시작된다.

---

### 리렌더링
최초 렌더링 이후 발생하는 **모든 후속 렌더링**을 의미한다.  
리렌더링은 다음과 같은 조건에서 발생한다.

---

#### 리렌더링이 발생하는 경우 1) 클래스 컴포넌트의 `setState()` 실행 시
- `setState()`는 state 변경을 트리거하여 렌더링을 발생시킨다.
- 변경된 state에 따라 새로운 UI를 계산한다.

```jsx
this.setState({ count: this.state.count + 1 }) // → 리렌더링 발생
```

---

#### 리렌더링이 발생하는 경우 2) 클래스 컴포넌트의 `forceUpdate()` 실행 시
- `forceUpdate()`는 `shouldComponentUpdate` 검사를 **건너뛰고 강제 렌더링**을 발생시킨다.
- 일반적으로 `render()`가 state나 props 외의 값에 의존할 때 사용하지만,  
  **render 내부에서 호출하면 무한 루프에 빠질 수 있으므로 주의**해야 한다.

---

#### 리렌더링이 발생하는 경우 3) 함수 컴포넌트의 `useState()` setter 호출 시
- `useState`가 반환하는 **두 번째 인자(setter 함수)** 를 실행하면 리렌더링이 발생한다.

```jsx
const [count, setCount] = useState(0)
setCount(count + 1) // → 리렌더링 발생
```

---

#### 리렌더링이 발생하는 경우 4) 함수 컴포넌트의 `useReducer()` dispatch 실행 시
- `useReducer`는 `useState`와 동일하게 작동한다.  
  dispatch 실행 시 새로운 상태를 계산하고 렌더링을 트리거한다.

```jsx
const [state, dispatch] = useReducer(reducer, initialState)
dispatch({ type: 'INCREMENT' }) // → 리렌더링 발생
```

---

#### 리렌더링이 발생하는 경우 5) `key` prop 변경 시
- 리액트에서 `key`는 **리렌더링 시 동일한 형제 요소를 구분**하기 위한 식별자다.  
- `key`가 변경되면 해당 컴포넌트를 **새로운 컴포넌트로 인식**해 강제 리렌더링한다.

```jsx
{arr.map((v) => (
  <Child key={v} />
))}
```

> `key={Math.random()}` 처럼 매번 바뀌는 key를 사용하면  
> 리렌더링 때마다 모든 자식이 새로 생성되어 성능 저하를 초래한다.  
> 반대로 key가 없으면 React는 sibling 인덱스로만 비교하므로  
> 동일한 요소를 올바르게 인식하지 못할 수 있다.

---

#### 리렌더링이 발생하는 경우 6) props가 변경될 때
- 부모 컴포넌트로부터 전달된 **props 값이 달라지면 자식 컴포넌트도 리렌더링**된다.
- `React.memo`나 `useMemo`, `useCallback`을 이용하면 props 변화가 없을 때 불필요한 렌더링을 방지할 수 있다.

```jsx
function Child({ value }) {
  return <div>{value}</div>
}
```

---

#### 리렌더링이 발생하는 경우 7) 부모 컴포넌트가 리렌더링될 때
- 부모가 리렌더링되면 **자식도 기본적으로 리렌더링**된다.  
  (자식이 memoized되지 않았다면)
- 이는 React의 렌더링 모델상 정상적인 동작이며,  
  필요시 `React.memo`를 통해 자식 렌더링을 최적화할 수 있다.

---

### 렌더링이 발생하지 않는 경우

리액트는 **state나 props 변경을 감지해야만 렌더링을 수행**한다.  
따라서 다음과 같은 **단순 변수 변경**은 렌더링을 발생시키지 않는다.

```jsx
let index = 0

export default function App() {
  function handleClick() {
    index += 1 // 단순 변수 변경 → 렌더링 X
  }

  return (
    <>
      <button onClick={handleClick}>+</button>
      {/* 화면에는 계속 0으로 표시됨 */}
      {index}
    </>
  )
}
```

> React의 렌더링 트리거는 `useState`, `useReducer`, `setState` 등  
> **상태 변경 API를 통해서만 발생**한다.

---

#### 외부 상태 관리 라이브러리와 렌더링
- `MobX`, `Redux` 등은 자체 상태를 관리하지만,  
  상태 변경이 곧바로 React 렌더링으로 이어지지 않는다.
- 대신 **mobx-react**, **react-redux** 같은 “React 연결 패키지”가  
  상태 변경을 감지하여 React의 `setState` 기반 렌더링을 발생시킨다.
- Recoil 등 일부 라이브러리는 내부적으로 **useState 기반 렌더링 시스템**을 사용해  
  별도 연결 패키지 없이도 동작한다.

---

### 질문 및 토론 사항
- 부모 렌더링이 자식에게 전파되는 원리는?  
  React의 렌더링은 “부모의 재렌더 → 자식의 재호출”이라는 함수 호출 구조
  (그래서 성능 이슈가 생기는데, 만약 부모가 자주 렌더링되면 그 아래 모든 자식도 다시 호출되기 때문에 큰 트리 구조에선 성능 부하가 생기게 됨.)
