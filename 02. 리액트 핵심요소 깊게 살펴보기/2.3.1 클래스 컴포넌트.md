## 2.1.1 클래스 컴포넌트

### 핵심 개념 요약

대부분의 리액트 개발자들이 클래스 컴포넌트를 사용하지 않고 있지만, 16.8 미만으로 작성된 코드에서는 대부분이 클래스 컴포넌트로 개발되어 있다. 

**기본적인 클래스 컴포넌트의 구조**

```jsx
import React from 'react'

class SampleComponent extends React.Component { 
	render() {
		return <h2>Sample Component</h2>
	}
}

// extends 구문에 넣을 수 있는 클래스 - React.Component, React.PureComponent
```

**props, state, 메서드 정의**

constructor() 

- 컴포넌트 내부에 이 생성자 함수가 있다면 컴포넌트가 초기화되는 시점에 호출
- 컴포넌트의 **state를 초기화**할 수 있음
- super() 호출을 통해 상위 컴포넌트에 접근 가능
- 메서드에 `this`를 바인딩(bind)하는 작업을 함

- *constructor 가 없어도 state 초기화가 가능할까?*
    
    ES2022에 추가된 클래스 필드 문법이 도입되면서, 별도의 초기화 과정을 거치지 않아도 클래스 내부에서 필드를 선언할 수 있게 도와준다.
    

props 

- **props**: 함수에 인수를 넘기는 것과 비슷하게, 컴포넌트에 특정 속성을 전달하는 용도
- 부모 컴포넌트로부터 전달받는 읽기 전용 데이터

state :

- 클래스 컴포넌트 내부에서 관리하는 값 (항상 객체여야 함)
- `state`가 변경되면 컴포넌트가 다시 렌더링(re-rendering) 됨

**클래스 컴포넌트의 생명주기 메서드**

render() : 

- 생명주기 메서드 중 **가장 중요한 필수 값**
- 이 함수는 컴포넌트가 UI를 렌더링하기 위해 쓰임
- **순수함수**여야 하며 부수 효과가 없어야 함
- state를 직접 업데이트하는 this.setState 호출하면 안 됨

**주요 생명주기** 

[React Lifecycle Methods diagram](https://projects.wojtekmaj.pl/react-lifecycle-methods-diagram/)

1. **마운트 (Mounting):** 컴포넌트가 생성되어 DOM에 삽입될 때
    - `constructor()`
    - `render()`
    - **`componentDidMount()`**: 컴포넌트가 DOM에 렌더링된 직후 호출 (API 요청, DOM 조작 등 부수 효과 수행)
2. **업데이트 (Updating):** `props`나 `state`가 변경될 때
    - `render()`
    - **`componentDidUpdate()`**: 리렌더링이 완료된 후 호출 (props, state 변경에 따른 부수 효과 수행)
3. **언마운트 (Unmounting):** 컴포넌트가 DOM에서 제거될 때
    - **`componentWillUnmount()`**: 컴포넌트가 소멸하기 직전에 호출 (이벤트 리스너 제거, 타이머 해제 등 정리 작업 수행)
    
    ---
    
4. **에러 경계 (Error Boundaries)**
    - 하위 컴포넌트 트리에서 발생하는 자바스크립트 에러를 처리하기 위한 특수 생명주기 메서드 (함수형 컴포넌트에는 없으며 클래스 컴포넌트로만 구현 가능)
    - **`static getDerivedStateFromError(error)`**:
        - 에러가 발생했을 때 **대체 UI(fallback UI)를 렌더링**하기 위해 사용
        - `render` 단계에서 호출되므로, **부수 효과를 발생시키면 안 됨**
        - 에러 발생 시 업데이트할 `state` 값을 반환
    - **`componentDidCatch(error, errorInfo)`**:
        - 에러가 발생했을 때 **에러 로깅**과 같은 부수 효과를 수행하기 위해 사용 됨
        - `commit` 단계에서 호출 (e.g., `console.error(errorInfo.componentStack)`)
        - **주의** : Error Boundary는 **자신**의 에러, **이벤트 핸들러** 내부의 에러, **비동기** 코드(e.g., `setTimeout`)의 에러는 잡아낼 수 없다.

**이벤트 핸들러와 `this` 바인딩**

클래스 컴포넌트에서 메서드를 이벤트 핸들러(예: `onClick`)로 사용할 때 `this`가 컴포넌트 인스턴스를 가리키도록 해야 함

**1. `constructor`에서 `bind`하기**

- 생성자에서 `this.handleClick = this.handleClick.bind(this);`와 같이 `bind` 메서드를 사용해 `this`를 명시적으로 묶어줌

**2. 화살표 함수(Arrow Function) 사용**

- `handleClick = () => { ... }`와 같이 클래스 필드(class field)로 화살표 함수를 사용하면, 함수가 선언될 때의 `this`가 고정되므로 `bind`가 필요 없음

**3. `render` 메서드 내 인라인 화살표 함수 (권장하지 않음)**:

- `<button onClick={() => this.handleClick()}>`처럼 `render` 내부에 직접 화살표 함수를 작성하는 방식
- **단점**: 렌더링이 일어날 때마다 **새로운 함수가 생성**되어 성능 최적화를 방해할 수 있으므로 지양하는 것 좋다.

**클래스 컴포넌트의 한계**

- **데이터 흐름 추적이 어려움**: `state`와 관련된 로직이 `componentDidMount`, `componentDidUpdate` 등 여러 생명주기 메서드에 흩어져 있어 코드를 이해하기 어려움
- **애플리케이션 로직 재사용이 어려움**: 상태 관련 로직을 재사용하기 위해 HOC(Higher-Order Components)나 Render Props 같은 패턴을 사용해야 했으며, 이는 "래퍼 지옥(wrapper hell)"을 유발하여 컴포넌트 구조를 복잡하게 만듬
- **컴포넌트 크기 증가**: 기능이 많아질수록 컴포넌트의 코드가 기하급수적으로 커지고 복잡해 짐
- **`this`와 클래스 개념의 어려움**: 자바스크립트의 `this` 바인딩은 초보자에게 혼란을 줄 수 있으며, 함수에 비해 클래스 문법 자체가 상대적으로 더 복잡함
