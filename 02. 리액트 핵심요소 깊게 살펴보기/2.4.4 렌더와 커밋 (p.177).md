## 2.4.4 렌더와 커밋

### 핵심 개념 요약

**React 렌더링의 2단계**

React의 렌더링은 크게 **렌더(Render) 단계**와 **커밋(Commit) 단계**로 나뉘어 진다.

- **렌더 단계 (Render Phase)**
    - 컴포넌트를 실행(호출)하여 렌더링하고, 이 결과(새로운 가상 DOM)를 **이전 가상 DOM과 비교**
    - 비교 항목은 **type, props, key** 세 가지
    - 이 중 하나라도 변경되면, 해당 컴포넌트를 "변경이 필요한 컴포넌트"로 체크
- **커밋 단계 (Commit Phase)**
    - 렌더 단계에서 체크된 변경 사항을 **실제 DOM에 적용**하여 사용자에게 보여줌
    - 이 단계가 완료된 후, React 내부 참조가 업데이트되고 생명주기 메서드(`componentDidMount`, `componentDidUpdate`)나 훅(`useLayoutEffect`)이 호출됨

**렌더링 ≠ DOM 업데이트**

**‘React 렌더링이 항상 실제 DOM 업데이트로 이어지지는 않는다’**

- **이유:** 렌더 단계에서 컴포넌트를 실행하고 가상 DOM을 비교했지만, **아무런 변경 사항이 감지되지 않으면(type, props, key가 모두 동일하면) 커밋 단계를 생략 함**
- **결과:** React 컴포넌트는 렌더링되었지만(렌더 단계 실행), 브라우저의 DOM은 업데이트되지 않는(커밋 단계 생략) 상황이 발생할 수 있다.

**동기식 렌더링과 동시성 렌더링**

- 동기식 렌더링 (Synchronous Rendering)
    - **전통 방식:** React의 렌더링은 **동기식(synchronous)**으로 작동
    - **문제점:** 렌더링 과정이 길어지면, 이 작업이 끝날 때까지 브라우저의 다른 모든 작업을 차단(blocking)하여 애플리케이션 성능 저하와 사용자 경험 악화로 이어 짐
    - **문제:** 만약 렌더링이 비동기로 처리되어 순서가 보장되지 않으면, 사용자가 일관되지 않은 UI(일부만 변경된 화면)를 볼 수 있는 문제가 발생
- 동시성 렌더링 (Concurrent Rendering - React 18)
    - **새로운 방식 (React 18):** **동시성 렌더링(concurrent rendering)**이 도입
    - **핵심:** **렌더 단계를 비동기(asynchronous)로** 작동시킬 수 있게 됨
    - 이를 통해 React는 특정 렌더링 작업의 **우선순위를 낮추거나, 중단, 재시작, 또는 포기**할 수 있음
    - 무거운 렌더링 작업이 브라우저를 차단하지 않고 백그라운드에서 처리될 수 있으므로, 사용자는 **더욱 매끄러운 사용자 경험**을 누릴 수 있다.

**결론**

React는 렌더링(변경 계산)과 커밋(DOM 적용) 단계를 분리하며, React 18부터는 렌더 단계를 비동기(동시성)로 처리하여 브라우저 차단 없이 더 나은 성능을 제공할 수 있게 되었다.

### 질문 및 토론 사항

- ‘불필요한 렌더링’은 정말 나쁜 것인가?
    - `memo`, `useCallback`, `useMemo` 등을 사용해 '불필요한 렌더링(렌더 단계 실행)'을 막는 최적화가 항상 필요할까?
    - 과도한 메모이제이션(memoization)이 코드 복잡성을 높이고 미미한 성능 이득만 주는 것은 아닐까?
