## 2.4.5 일반적인 렌더링 시나리오 살펴보기

### 핵심 개념 요약

#### 상황 설명
- 컴포넌트 A → B → C → D로 이어지는 **부모-자식 트리 구조**가 있다고 가정.
- B 컴포넌트 내부의 버튼을 클릭하면 `counter` 값이 증가하고,  
  이때 리액트에서 어떤 순서로 렌더링이 일어나는지를 살펴보는 예제다.

#### 예제 코드 구조

```jsx
import { useState } from 'react'

export default function A() {
  return (
    <div className="App">
      <h1>Hello React!</h1>
      <B />
    </div>
  )
}

function B() {
  const [counter, setCounter] = useState(0)

  function handleButtonClick() {
    setCounter(prev => prev + 1)
  }

  return (
    <label>
      <C number={counter} />
      <button onClick={handleButtonClick}>+</button>
    </label>
  )
}

function C({ number }) {
  return (
    <div>
      {number} <D />
    </div>
  )
}

function D() {
  return <>리액트 재밌다!</>
}
```

---

### 렌더링 발생 단계 상세 흐름

B 컴포넌트에서 버튼 클릭 → `setCounter()` 호출 시 다음과 같은 단계로 렌더링이 일어난다:

1. **B 컴포넌트의 setState 실행**
   - 상태 변경이 일어나 렌더링이 필요하다고 표시됨.

2. **B 컴포넌트가 렌더링 큐에 등록됨**

3. **리액트는 트리 루트(A)부터 렌더링 여부를 검사**
   - A는 업데이트 필요 없음 → 스킵

4. **B 컴포넌트가 “업데이트 필요”로 체크됨 → 리렌더링 실행**

5. **B 컴포넌트가 C 컴포넌트를 반환**

6. **C 컴포넌트의 props(number)가 변경됨 → 업데이트 필요 체크됨 → 리렌더링**

7. **C가 D를 렌더링에 포함시키므로 D도 렌더링됨**
   - D는 props 받지 않지만, **부모가 새로 렌더링되었기 때문에 자동으로 렌더링됨**

---

### 핵심 결론: 부모 렌더링 → 자식 렌더링

리액트의 기본 동작 특성  
> **부모가 리렌더링되면, 자식도 기본적으로 모두 리렌더링된다.**  
> (props 변화 여부와 관계 없음)

즉, 상위 컴포넌트에서 상태 업데이트가 일어나면  
트리 구조 전체의 하위 부분들이 연쇄적으로 리렌더링될 수 있다.

이 동작은 **렌더링은 비용이 크지 않게 설계되어 있다는 전제**에서 정상적인 리액트 동작이다.

---

### memo를 적용하면 어떻게 될까?

```jsx
const D = memo(() => {
  return <>리액트 재밌다!</>
})
```

- 부모(C)가 렌더링되더라도  
  `D`는 **props가 변경되지 않는 한 렌더링을 건너뛴다.**
- 정확히 말하면:
  - 렌더 단계(Render Phase)에서는 비교가 수행됨
  - 하지만 memo 비교로 인해 변경 없음 → **커밋 단계(Commit Phase) 생략됨**

즉, `memo`는 **불필요한 DOM 업데이트와 렌더링 비용을 줄여주는 최적화 도구**다.
