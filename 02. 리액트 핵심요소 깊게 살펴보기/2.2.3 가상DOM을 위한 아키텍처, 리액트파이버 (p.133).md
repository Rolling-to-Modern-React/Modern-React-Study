## 2.2.3 가상 DOM을 위한 아키텍처, 리액트 파이버 (React Fiber)

### 핵심 개념 요약

가상 DOM을 만드는 과정을 리액트는 어떻게 처리하고 있을까? 리액트는 여러 번의 렌더링 과정을 압축해 어떻게 최소한의 렌더링 단위를 만들어 내는 것일까? 이러한 가상 DOM과 렌더링 과정 최적화를 가능하게 해주는 것이 바로 리액트 파이버(React Fiber)다.

#### React Fiber란?
- **React Fiber**는 리액트의 **가상 DOM(Virtual DOM)** 을 효율적으로 관리하기 위한 **재조정(Reconciliation)** 엔진이다.  
- 내부적으로는 **하나의 자바스크립트 객체(FiberNode)** 로 구현되어 있으며,  
  가상 DOM과 실제 DOM의 차이를 비교해 **최소한의 렌더링만 수행**하도록 도와준다.

> **Reconciliation(재조정)**  
> 가상 DOM과 실제 DOM을 비교하여 변경된 부분만 찾아 업데이트하는 과정.

---

#### Fiber의 역할
Fiber의 목표는 리액트 앱에서 발생하는 **애니메이션, 사용자 입력, 레이아웃 등 복잡한 렌더링 작업**을  
더 효율적이고 반응성 있게 처리하는 것이다.

Fiber는 다음과 같은 일을 수행한다.

1. **작업을 작은 단위로 분할**해 처리한다.  
2. **작업의 우선순위를 지정**한다.  
3. **일시 중단·재개·폐기**가 가능하다.  
4. **비동기 렌더링(Asynchronous Rendering)** 을 지원한다.

---

#### 기존 스택 알고리즘의 한계
- **이전 리액트(V15 이하)** 는 렌더링을 “스택(Stack)” 형태로 동기적으로 처리했다.  
- 즉, 한 번 렌더링이 시작되면 **중단할 수 없었다.**
- 예를 들어, 사용자가 `<input>`에 입력 중 자동 검색 UI가 렌더링되는 경우,  
  네트워크 요청(fetch)과 UI 렌더링이 모두 스택에 쌓이면 입력 지연(lag)이 발생할 수 있었다.

> 문제점: 싱글 스레드 환경에서 동기 렌더링은 사용자 입력을 블로킹함.

---

#### Fiber의 구조
Fiber는 **하나의 작업 단위(Unit of Work)** 를 나타내며, 리액트는 이를 순차적으로 처리한다.

- **렌더 단계 (Render Phase)**  
  - 비동기적으로 수행됨  
  - 작업 단위 분할, 우선순위 지정, 중지/재개/폐기 등의 로직 수행  
- **커밋 단계 (Commit Phase)**  
  - 동기적으로 수행됨  
  - 실제 DOM 변경 및 화면 반영 (`commitWork()` 실행)  

> 이 두 단계는 이후 2.4절 *“렌더링은 어떻게 일어나는가?”* 에서 자세히 다룸.

---

#### FiberNode의 실제 구조

```js
function FiberNode(tag, pendingProps, key, mode) {
  // Instance
  this.tag = tag
  this.key = key
  this.type = null
  this.stateNode = null

  // Fiber
  this.return = null
  this.child = null
  this.sibling = null
  this.index = 0

  this.pendingProps = pendingProps
  this.memoizedProps = null
  this.memoizedState = null
  this.updateQueue = null
  this.alternate = null
}
```

- 단순한 **JS 객체 형태**로 구현되어 있으며,  
  렌더링에 필요한 모든 상태 정보(tag, props, state 등)를 담고 있다.

---

#### 주요 속성 정리

| 속성명 | 설명 |
|:--|:--|
| `tag` | 파이버가 어떤 요소를 나타내는지 식별 (컴포넌트 / DOM 노드 등) |
| `stateNode` | 실제 DOM 노드나 클래스 인스턴스 참조 |
| `child`, `sibling`, `return` | 파이버 간 관계(부모-자식-형제)를 연결하는 트리 구조 |
| `index` | 형제(sibling) 간 순서 |
| `pendingProps` | 아직 처리되지 않은 props |
| `memoizedProps` | 렌더링 완료 후 확정된 props |
| `updateQueue` | setState, callback, DOM 업데이트 등 예약된 작업 목록 |
| `memoizedState` | 훅(Hook) 정보 등 상태 저장 |
| `alternate` | **현재 트리와 workInProgress 트리 간 연결** (더블 버퍼링용) |

> 나머지는 리액트의 다양한 컴포넌트 타입(Function, Class 등)을 나타낸다.

#### 파이버 트리 (Fiber Tree)
리액트 내부에는 **2개의 파이버 트리**가 존재한다.

1. **current 트리** — 현재 UI를 나타내는 트리  
2. **workInProgress 트리** — 업데이트 중인 새로운 트리  

업데이트가 완료되면 **포인터만 교체**하여  
`workInProgress` → `current`로 전환하는데,  
이를 **더블 버퍼링(Double Buffering)** 기법이라 부른다.

> **Double Buffering**  
> 미리 보이지 않는 곳에서 다음 화면을 그린 뒤, 완성되면 교체하는 방식.  
> 렌더링 도중 불완전한 UI가 노출되지 않도록 함.

#### 파이버 트리 순회 흐름 (렌더링 과정)

JSX 예시:
```jsx
<A1>
  <B1>안녕하세요</B1>
  <B2>
    <C1>
      <D1 />
      <D2 />
    </C1>
  </B2>
  <B3 />
</A1>
```

작업 순서:
1. `A1`의 `beginWork()` 실행 → 자식 `B1`로 이동  
2. `B1`은 자식이 없으므로 `completeWork()` 실행  
3. 형제 `B2`로 이동 → 내부 `C1` → `D1`, `D2` 순으로 진행  
4. 하위부터 `completeWork()` 실행 후 상위로 반환  
5. `B3` 처리 후 `A1`로 돌아가 최종 `completeWork()` 실행  
6. 마지막으로 `commitWork()`에서 변경 사항을 DOM에 반영

이 과정을 반복하며 트리가 완성된다.

---

#### 업데이트 시 동작
- `setState()` 등으로 상태 변경이 발생하면,  
  리액트는 기존 `current` 트리를 기준으로  
  새로운 `workInProgress` 트리를 생성한다.
- 가능하면 기존 Fiber 객체를 **재사용(reuse)** 하고,  
  필요한 속성만 갱신하여 리소스를 절약한다.
- 작업은 **우선순위(priority)** 에 따라 스케줄링되어,  
  사용자 입력/애니메이션은 빠르게,  
  무거운 렌더링은 뒤로 미뤄진다.

---

### 질문 및 토론 사항
- Fiber 덕분에 생긴 실제 효과?<br>
  렌더링 중단 / 재개 가능, 업데이트 우선순위 조절, 시간 분할, Concurrent Mode 기반<br><br>
  
- 이전 리액트(V15 이하)는 그럼 Virtual DOM이 맞는지?<br>
  Stack Reconciler 시절 -> 두 트리를 재귀적으로 비교 -> 렌더링 중엔 중단이 불가능 -> 실질적으로는 그냥 트리 전체를 다시 계산하는 함수 호출 수준<br>
  Fiber 이후 — “진짜 Virtual DOM 시스템으로 진화”<br>
  “가상 DOM을 계산”하던 구조에서 “가상 DOM 자체가 렌더링 스케줄링을 관리”하는 구조로 진화된 것<br>
  Fiber 이전 React → Virtual DOM은 단순히 “렌더링 결과를 비교하는 데이터 구조”<br>
  Fiber 이후 React → Virtual DOM은 “상태 + 스케줄링 + 렌더링 흐름을 모두 관리하는 작업 엔진”
